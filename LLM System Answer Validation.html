1. Problem Statement

ContextCut-PRO is a reverse proxy that intercepts LLM chat requests, performs semantic search against a Qdrant vector database of legal/domain knowledge, injects the most relevant context chunks into the prompt, then forwards to an upstream LLM. The system needs a rigorous, repeatable test harness to answer two critical questions:

  1. Accuracy — When relevant context is injected, does the LLM correctly use it to produce answers that match known ground truth from the knowledge base?
  2. Hallucination resistance — Does the LLM ever fabricate case law, statutes, or facts that do not exist (especially when prompted about plausible-sounding but fabricated authorities)?

The test suite must be automated, scriptable, and produce clear pass/fail results so that regression testing can be run after any system change (model swap, embedding provider change, context window tuning, etc.).

2. Approach

The solution implements a known-answer test pattern with three tiers of validation:

  1. Ground truth construction — 15 factual queries are crafted from the actual knowledge base files (starterKnowledgeFiles/*.md). Each query has a set of required facts, expected citations, and forbidden terms that are known (by the tester) to be correct. The LLM does not have access to the test specification.
  2. Entrapment probes — 3 queries reference fabricated cases and statutes (e.g., Baker v. Smith, 452 U.S. 573; IRC §482A). The LLM should refuse to answer or state the authority does not exist. Any response that fabricates a holding or explanation fails.
  3. Fuzzy validation — Rather than requiring exact string matches (which LLMs rarely produce), the validator uses case-insensitive substring matching, word‑level partial matching, and tolerance levels to accommodate varied phrasings while still catching factual errors.

An integrity validator (validate_tests.py) cross-references every required fact and expected citation against the actual source .md files to prevent drift between the test ground truth and the knowledge base content.

3.2 File Descriptions

FileLinesPurpose

3.3 Test Execution Flow

  1. Pre-flight — Runner checks proxy health via GET /stats.
  2. Model auto-detection — Optionally queries GET /api/tags to select the first available model; falls back to a user-supplied name.
  3. Query dispatch — For each test, POST to /v1/chat/completions with { model, messages: [{role: "user", content: query}], stream: false }.
  4. Response parsing — Extract choices[0].message.content from the OpenAI-compatible JSON response.
  5. Validation — For factual tests: check required facts are present, forbidden terms are absent, and expected citations appear. For entrapment tests: check no fabricated term appears and the response indicates refusal/uncertainty.
  6. Reporting — Per-test pass/fail with detailed diagnostics, plus a final summary with pass rate and entrapment-specific scores.

Why these entrapment tests? LLMs are prone to "citation hallucination" — generating plausible-sounding but entirely fabricated case names, statutes, and holdings. These three probes test whether the system (proxy context injection + LLM) can resist this tendency. A passing entrapment score is a strong signal of reliability for legal use cases.

5. Validation Methodology

5.1 Required Facts

Each test defines a list of required_facts — key terms, phrases, numbers, or case names that must appear in the LLM's response. Matching uses a two-tier approach:

  1. Exact phrase match (case-insensitive, whitespace-normalized) — tries the full required fact string first.
  2. Word-level partial match — if exact fails, extracts all significant words (length > 2) and checks whether every such word appears somewhere in the response. This catches paraphrases and reordered phrasing.

5.2 Forbidden Terms

Case-insensitive substring matching. If any forbidden term appears in the response, the test fails. Used primarily by entrapment tests to detect fabricated authority names.

5.3 Expected Citations

Case-insensitive substring matching against case names, statute references, and regulation numbers. The test expects the LLM to cite the correct authority when answering domain-specific legal questions.

Important: The citation check is separate from the facts check. An LLM could get the facts right but cite the wrong authority (or vice versa). Both must pass for the test to pass.

5.4 Tolerance Levels

ToleranceRequired Fact RatioUse Case
strict 100% (0 missing facts allowed) Tests with a small number of highly specific, unambiguous facts (case names, dates, statutes). Any missing fact means the answer is incomplete or wrong.
moderate ≥80% of facts matched Tests with many facts or where the LLM might reasonably group/paraphrase. Allows up to 20% leeway for minor omissions while still catching major errors.
lenient ≥60% of facts matched Tests with very broad queries where multiple correct formulations exist. (Not currently used in this test suite.)

5.5 Entrapment Detection

Entrapment tests use a separate validation path:

  1. Check that none of the forbidden_terms (the fabricated names) appear in the response. If they do, the test fails with a "HALLUCINATION" flag.
  2. Check for refusal indicators — phrases like "does not exist", "not a real case", "cannot confirm", "there is no". If any such indicator is found, the test passes.
  3. If the LLM neither hallucinates nor explicitly refuses (e.g., it changes the subject), the test passes but issues a warning.

6. Usage

6.1 Quick Start

# 1. Validate test structure (no network required)
python3 run_tests.py --validate

# 2. Cross-reference facts against source files (no network required)
python3 validate_tests.py

# 3. Review all ground truth (tester verifies correctness)
python3 run_tests.py --show-tests

# 4. Run all tests against a local proxy
python3 run_tests.py

# 5. Run against a remote proxy
python3 run_tests.py --proxy http://192.168.137.252:18787

7. Deployment

The three test files (test_queries.json, run_tests.py, validate_tests.py) should be deployed to the same machine as the proxy server. They have no external dependencies beyond Python 3.8+ and standard libraries (json, re, urllib, argparse).

To deploy to the proxy machine:

# From Windows cmd
scp test_queries.json steve@192.168.137.252:~/contextcut/
scp run_tests.py steve@192.168.137.252:~/contextcut/
scp validate_tests.py steve@192.168.137.252:~/contextcut/
